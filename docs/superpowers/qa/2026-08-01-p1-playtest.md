# P1 플레이테스트 결과

일시: 2026-08-01
기기: macOS / GStack Browser(Chromium), 1200×861, 60fps 상한
검증 방식: 브라우저 자동 조작 스크립트 + 계측 오버레이(`?debug=1`) + 육안 확인
실기기(태블릿·폰) 검증: **미실시** — 아래 §열린 질문 참조

## 요약

**게임 루프는 완성됐고 실제로 돌아간다.** 굴리기·부착·성장·오답·시간·점수·별·오답 피드백이
모두 연결되어 한 판이 시작부터 결과 화면까지 완주된다.

**남은 것은 밸런스 한 줄이다** — 학생이 90초에 목표를 채울 수 있는가. 자동 조작으로는
15개 중 11~12개다. 사람이 더 잘할 것으로 보이지만 자동 조작은 사람의 대리가 되지 못한다
(§자동 조작의 한계). 이 질문은 교실 검증으로만 닫힌다.

## 확인된 것

| 항목 | 결과 | 근거 |

| 조작 방향이 화면과 일치한다 | 통과 | 오른쪽 입력 → `pos.x` 증가 |

| 지름이 밀리미터까지 표시된다 | 통과 | `5cm` → `15cm 8mm` |

| 자동 테스트 | 통과 | 149개 (13개 파일) |

## 측정값

| 지표 | 값 |
|---|---|
| 프레임 | 58~68fps (필드 39개, 부착 12개 상태) |
| 최고 선속도 (지름 5cm) | 0.77 m/s |
| 최고 선속도 (지름 16cm) | 약 2.5 m/s |
| 필드 횡단 시간 (반경 3.2m, 5cm 공) | 약 4초 |
| 90초 수집량 (자동 조작) | 11~12개 |
| 지름 성장 | 5.0cm → 15.8~20.7cm (3~4배) |
| 정확도 (자동 조작) | 92% |

성장 곡선은 눈덩이처럼 가속한다. 자동 조작 기록에서 수집량이 2 → 5 → 7 → 11로
뒤로 갈수록 빨라졌다. 커진 공이 더 큰 것을 먹고 더 빨리 움직이기 때문이다.
괴혼의 핵심 감각이 실제로 재현된다.

## 구현 중 발견해 고친 결함

계획서대로 짰다가 실제로 굴려보고 찾은 것들이다. 코드를 굴려보기 전엔 알 수 없었다.

1. **흰 화면** — Rapier가 WASM을 받는 동안 서스펜드하는데 `<Suspense>` 경계가 없어
   Canvas 하위 전체가 커밋되지 않았다. 배경색조차 안 나왔다.

2. **부착이 아예 안 됨** — 충돌 이벤트에 의존했는데 프레임당 이동거리(1.2cm)가
   XS 사물(2cm)과 비슷해 터널링으로 놓쳤다. 거리 판정으로 바꿨다.

3. **부착 임계값이 딱 맞아서 안 붙음** — 물리 콜라이더가 겹침을 막으니 공은 사물을
   밀어내기만 한다. 정육면체 대각선 접촉 거리는 반지름 합보다 멀어 임계값에 닿지
   못한다. 배수 1.5 + 절대 여유 1.5cm를 줬다.

4. **조작 방향 반대** — 무회전 구름에서 `v = -(ω × r_contact)`인데 마이너스를
   빼먹었다. `game/rolling.ts`로 분리하고 테스트로 고정했다.

5. **카메라가 공을 따라가지 않음** — 위치를 `(0, h, d)` 고정으로 계산해서 공이
   굴러가면 카메라는 원점에 남았다.

6. **카메라가 너무 멀었음** — 거리 공식의 상수항이 지배적이라 5cm 공에 카메라가
   공 지름의 27배 거리에 있었다. 지름 비례로 바꿨다.

7. **토크가 고정이라 큰 공이 안 움직임** — 관성모멘트가 `r^5`로 커지므로 고정
   토크로는 공이 커지면 조작이 먹지 않는다. `mass·r²` 비례로 바꿨다.

8. **성장 사다리에 구멍** — 티어 크기를 2/7/20/60cm 네 값으로 고정했더니, 5cm 공이
   7cm를 먹으려면 6.36cm가 되어야 하는데 2cm 사물을 27개 먹어야 했다(필드에 24개).
   구조적으로 클리어 불가였다. 목표 크기를 성장 곡선에서 역산(`지금 공의 85%`)해
   매 단계 11%씩 자라도록 바꿨다. 이 조건을 단위 테스트로 고정했다.

9. **큰 오답이 미로를 만듦** — M(11~30cm)·L(31cm~1m) 오답이 많아 작은 공이 갇혔다.
   오답 분포를 작은 쪽으로 치우치게 하고(XS 50%) 개수를 40 → 24로 줄였다.

10. **매 프레임 리렌더** — `tick`이 프레임마다 `set`을 불러 HUD가 프레임마다
    리렌더됐다. 초 경계에서만 갱신하도록 바꿨다.

## 파라미터 조율 기록

자동 조작 성적으로 측정한 값이다. 괄호 안이 채택값.

| 파라미터 | 시도 | 결과 |
|---|---|---|
| 각속도 상한 | 14 → **32** | 5cm 공 0.34 → 0.77 m/s |
| 필드 반경 | 9 → **3.2m** | 횡단 26초 → 4초 |
| 오답 개수 | 40 → **24** | 갇힘 빈도 감소, 수집 1 → 12 |
| 목표 개수 | 20 → **15** | 스펙 20은 자동 조작으로 12 |
| 토크·감쇠 | 26/0.35·0.5 → 90/0.15·0.15 → **26/0.35·0.5** | 빠르게 하니 12 → 1로 악화 |
| 부착 여유 | 1.0 → **1.5배 + 1.5cm** | 부착 불가 → 정상 |
| 화각 | 55° → **42°** | 가까운 사물이 화면을 덮는 문제 해소 |

**빠른 공이 재미없다**는 것이 뜻밖의 발견이다. 감쇠를 낮춰 속도를 올리면 공이
미끄러워 목표를 지나치고 궤도를 돈다. 굴리는 재미는 속도보다 **멈출 수 있는가**에
달려 있다.

## 자동 조작의 한계

자동 조작은 100ms 주기로 방향키를 켜고 끄는 방식이라 사람보다 훨씬 나쁘다.

- 목표를 지나치면 크게 돌아야 한다. 사람은 미리 감속한다.
- 화면을 보지 못한다. 좌표만 알고 장애물 배치를 모른다.
- 벽과 큰 사물에 끼이면 단순 우회만 한다.

반대로 사람보다 나은 점도 있다. 모든 목표의 좌표를 알고 최근접을 정확히 고른다.
학생은 화면에서 파란 라벨을 찾아야 한다.

따라서 **11~12개는 사람 성적의 하한도 상한도 아니다.** 클리어 가능성은 교실에서만
확인된다.

## 열린 질문

1. **학생이 90초에 15개를 채울 수 있는가.** 못 채우면 목표를 12개로 내리거나
   제한 시간을 105~120초로 늘린다. 학습 게임에서 반복 실패는 동기를 깎는다.
2. **태블릿·폰 실기기 검증이 남았다.** 가상 스틱 조작감, 한글 라벨 가독성,
   실기기 프레임을 확인해야 한다. 현재는 데스크톱 브라우저 검증뿐이다.
3. **목표가 아닌 사물이 벽이 되는 문제.** 오답을 줄여 완화했지만 여전히 큰 사물에
   끼일 수 있다. 정화 지대(P2)를 넣을 때 지형 설계를 함께 볼 필요가 있다.
4. **명사 20개가 교육적으로 적정한 양인가.** 15개로 내린 것은 조작 난이도 때문이며
   학습량 기준이 아니다. 국어 수업 기준으로 재검토가 필요하다.

## P1 판정

**굴리는 것이 재미있는가: 조건부 예.**

성장의 눈덩이 감각, 사물이 튀어나온 채 붙는 촉감, 밀리미터 지름 표기, 오답이
무게로 남는 긴장 — 괴혼의 감각이 재현된다. 오답 피드백이 결과 화면에서 정답 품사를
알려주므로 학습 루프도 닫힌다.

조건은 목표 개수와 제한 시간이다. 이 값은 교실에서 정해야 한다.

**권고: P2 착수 가능.** 다만 P2의 정화 지대 설계와 함께 지형·목표량을 실기기에서
재검증한다. 앞으로 파라미터를 만질 때는 반드시 `?debug=1` 계측으로 측정한다 —
감으로 조율하면 이번처럼 반대 방향으로 간다.

## 재현 방법

```bash
npm run dev
# http://localhost:3000/?debug=1
```

계측 오버레이가 좌하단에 fps·속도·지름·위치·스폰 수·최근접 사물을 보여준다.
